## Phase 1 — Firebase persistence
The repository includes a starter integration:
- `firebase-config.js`
- `firebase-bridge.js`
- `firestore.rules`
- `firebase.json`
- `FIREBASE_SETUP.md`

Review and improve this integration rather than discarding it.

### Firebase requirements
Use:
- Firebase Authentication
- Cloud Firestore
- Google sign-in initially
- Vercel for hosting the frontend

Keep localStorage as a fallback/cache.

### Security model
Each signed-in user can only access their own document tree.

Primary state document:
`users/{uid}/app/state`

Do not use public Firestore rules. Do not store bank credentials, MFA codes, or private banking secrets.

### Sync behavior
- Local edits update the UI immediately.
- Local state saves immediately to localStorage.
- Cloud writes are debounced.
- On sign-in, load Firestore state if it exists.
- If Firestore is empty, seed it from current local state.
- Show clear cloud status: Local only / Connect Firebase / Syncing / Cloud synced / Error.
- Never destroy local data because Firebase is temporarily unavailable.

## Phase 2 — Normalize Firestore data
After the simple state-document sync works reliably, migrate to structured collections only if it clearly improves maintainability.

Recommended long-term structure:

```text
users/{uid}
  profile/main
  settings/main
  accounts/{accountId}
  transactions/{transactionId}
  recurringExpenses/{expenseId}
  incomeSources/{incomeId}
  goals/{goalId}
  forecastSnapshots/{snapshotId}
  developmentSpend/{spendId}
```

Do not perform this migration until the first Firebase persistence version is stable.

## Phase 3 — Screenshot transaction intake
Add a workflow for bank screenshots later. Do not automatically write AI-extracted transactions into the ledger.

Required flow:
1. User selects/uploads screenshot.
2. AI extracts candidate transactions.
3. System shows a Review & Approve screen.
4. User can edit date, description, amount, account, category, and pending/posted status.
5. Duplicate detection runs against existing transactions.
6. Only approved transactions are committed to Firestore.
7. Forecast recalculates after approval.

## Financial logic requirements
The core calculations must be deterministic, not generated by an LLM.

Maintain these separate concepts:
1. Available cash now
2. Pending / confirmed uncleared cash movements
3. Upcoming scheduled obligations
4. Confirmed future income
5. Pipeline / possible revenue — never count this as available cash

Forecast formula concept:

`available cash - confirmed outflows - scheduled obligations + confirmed inflows = projected cleared cash`

AI can explain the result, classify transactions, detect anomalies, and suggest attention items. AI must not silently alter balances or forecasts.

## Current planning model to preserve
- Separate NOFA and Personal finances.
- Owner withdrawals are not NOFA operating expenses.
- Client revenue is gross revenue; direct client service/API costs are deducted separately.
- Variable Oz/Warp build credits are development spending, not fixed recurring expenses.
- Canceled or paid-off recurring items remain historically visible but are excluded from future totals.
- Reserve targets and sinking funds are editable.
